# 验证记录与验收方法

## 原方案已经观察到的结果

2026-10-12，在 macOS 14.5 / Apple Silicon / UU 4.42.0 / ProxyBridge 4.0.0 / sing-box 1.14.3 上：

- 配置只包含四个指定 UU 签名标识。
- 原先绕入系统 TUN 后超时的 TCP 连接进入专用通道，本地网卡建立了对外连接。
- UU 的 UDP 流量进入专用通道。
- 一次由系统代 UU 发出的 DNS 查询保留 UU 有效应用身份，被扩展接收并经专用通道转发，约 21 毫秒收到包含 A 记录的有效响应。
- UU 主程序和 Server 的请求出现 HTTP 200；官方 CLI 报告已登录和 connected。
- 用户通过手机蜂窝网络重新连接 Mac，能进入桌面并操作。
- 手动调用启动顺序及重新加载专用 LaunchAgent 后，既有通道继续运行。
- 系统代理、系统 DNS 和其他已检查的既有启动配置前后保持一致。

这些是原部署环境的结果，不是新工具包在所有平台上的认证。原设备的路径、进程号、用户名、服务器连接明细和完整日志不随仓库公开。

## 新工具包的只读实机检查

源码的 41 项自动测试已通过，覆盖安装隔离、下载校验、启动顺序、规则核对、端口冲突及卸载范围。测试使用模拟系统命令和临时目录，未安装新通道。命令行帮助检查也已通过；各次 GitHub Actions 运行结果请查看仓库的 Actions 页面。

2026-10-13，使用新工具包的检查逻辑读取已长期运行的 ProxyBridge 扩展状态时，完整生命周期的定向日志查询超时。当前单次查询上限仍为 10 秒，未取得足够启动证据就拒绝自动打开 UU；大历史日志的读取性能问题尚未解决。查询超时不是规则已经失效的证据，也没有据此重启扩展或改变原部署配置。

遇到此情况，请查看运行目录中的 `logs/startup.log` 和 `logs/startup-error.log`。必要时，在可接受连接中断的情况下，通过 ProxyBridge 手动重连扩展后重试；工具不会自动重启第三方扩展，也不会因日志缺失或超时降低检查门槛。

新工具包生成的配置已使用现有官方 sing-box 1.14.3 执行 `check`，退出码为 0。这只证明配置通过该版本的静态校验，不是新工具包的真实安装、启动或远控验证。

## 新用户验收步骤

1. 记录自己的操作系统、CPU 架构、UU 和依赖版本，不公开设备标识。
2. 在通道停止时核对本地网络可用、端口空闲、所选 `enN` 网卡正确。
3. 安装后先核对生成的配置、Profile 和启动项路径；确认只配置四个 UU 规则。
4. 手动启动，检查日志顺序和 UU 实际连接；手机关闭 Wi-Fi 后重新建立会话并操作。
5. 在方便恢复的情况下，自行安排登录/重启测试。未登录桌面或 FileVault 未解锁时，不应把通道未启动当作通过。
6. 如需验证代理独立性，由使用者明确安排退出代理及恢复操作。观察新建远控会话，不只观察已有会话是否还活着。
7. 卸载测试前，先恢复 UU 代理设置并停用本 Profile，核对删除计划，再执行确认。

本工具本身不会通过停止用户的其他代理软件来自动完成这些测试。

## 启动检查的边界

健康检查使用独立 curl 参数，经本机专用端口请求 UU API，并保留证书验证。API 根路径的 HTTP 404 也可以证明 DNS、CONNECT 和 TLS 成功，但不证明账户登录或远控媒体通路完整。

ProxyBridge 保存的规则检查、进程身份检查和系统日志检查能发现部分错误。上游没有向本工具提供严格的逐规则运行确认接口；日志可能缺失、轮转或随版本变化。检测到后续停止/失败日志应拒绝认定就绪；即便未看到停止记录，也不能推导出持续隔离保证。

专用通道异常退出后可由 LaunchAgent 重新执行启动顺序。本项目不提供跨所有组件的 fail-closed 防泄漏机制，也不修改系统防火墙、路由或全局 DNS 来实现这种机制。
